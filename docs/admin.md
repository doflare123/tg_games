# Кабинет владельца

Вкладка «Кабинет» появляется у Telegram ID `930852883`. Прямая ссылка внутри приложения: `#admin` (также поддерживается `startapp=admin`). ID проверяется сервером через `verifiedPlayer(context)` и `requireAdmin`; аргументы запроса, username, состояние интерфейса и служебный флаг в теле запроса доступа не дают. Платформа отвечает за проверку подлинности Telegram endpoint context. Реальное облачное выполнение и авторизация на устройствах требуют отдельной проверки после публикации.

## Возможности

- Восемь недель активности, график партий и популярность игр. Текущая неделя сравнивается с таким же интервалом предыдущей, в UTC с понедельника.
- Серверные партии, результаты в рейтинге, уникальные игроки, посетители, впервые замеченные посетители, добавления и удаления бота из уникальных групп.
- Текущее число известных и активных групп, известных игроков и посетителей, блокировок и ожидающих уведомлений.
- Просмотр 14 представлений БД, поиск по показанным столбцам, по 25 строк на страницу. Игровые состояния, replay и исходные payload уведомлений не передаются в браузер.
- Снятие отдельного результата каждой игры, удаление ручного исправления, запрет новых результатов игрока и снятие запрета, отключение уведомлений группы, отмена ожидающего уведомления.

Редактирование выполняется через предварительный просмотр, обязательную причину и подтверждение. Изменение, подавление связанных уведомлений и журнал выполняются одним SQLite statement с триггером. Предварительное состояние сравнивается непосредственно при записи. Ключ запроса предотвращает повтор после потери ответа. Журнал содержит оператора, время, причину, предыдущее значение и применённое изменение. Публичного SQL endpoint нет.

Снятие результата сохраняет серверную партию со статусом `unranked`, исключает её из рейтинга и подавляет связанные уведомления. Ручное исправление удаляется, его показанные поля остаются в журнале. Запрет новых результатов не удаляет старые рекорды. Снятие запрета не восстанавливает отменённые уведомления. Включение групповых уведомлений остаётся в существующем интерфейсе администраторов группы с проверкой участия и прав. Уже доставленные сообщения и отправки, прошедшие последнюю проверку до изменения, нельзя отменить через кабинет.

## Подготовка облака

Ни одна из следующих команд не вызывается автоматически из `check` или `build`. Перед публикацией подготовить резервную копию БД стандартными средствами управления платформы.

1. `npm run check` — подготовить и проверить сборку.
2. Опубликовать код обычным процессом проекта (`npm run deploy`).
3. Отдельно просмотреть и применить изменения схемы (`npm run cloud:migrate`). Новые таблицы кабинета описаны в `src/server/platform/schema.ts`; также нужны все таблицы текущих игр.
4. `npm run admin:install` — посмотреть план без чтения credentials, сетевых запросов и изменений БД.
5. `npm run admin:install -- --apply` — явно установить таблицы, индексы и триггеры через аутентифицированный management API. CLI token берётся из `TGCLOUD_TOKEN` или `.tgcloud/credentials`, никогда не передаётся клиенту. Повторный запуск сохраняет первоначальное время начала учёта и существующие данные.
6. Проверить открытие кабинета владельцем и отказ другому аккаунту в настоящем Telegram. Проверку изменения проводить на отдельно созданной тестовой записи, не на пользовательском рекорде.

До завершения служебной миграции кабинет показывает сообщение о неподготовленной БД. Обычный профиль и игры продолжают работать без аналитики. Если хотя бы один обязательный триггер отсутствует, административные запросы отказывают в выполнении.

## Границы статистики

Посещения фиксируются при успешном вызове `getProfile`, а не при каждом нажатии. Один пользователь имеет одну строку на день UTC; повторные записи ограничены интервалом в пять минут. Посетители не обязательно играли. Длительно открытая вкладка без нового вызова профиля не является новым посещением следующего дня. У владельца нет скрытого исключения из статистики.

Групповые события берутся из `my_chat_member` с датой события Telegram и подавлением повторов. Изменение прав без выхода/входа не считается новым добавлением. Обнаружение группы по сообщению не считается добавлением бота. Старые даты добавления, история удалений и посещения до установки кабинета не восстанавливаются. Первая неделя учёта может быть неполной; сравнение посещений до накопления полной истории отключено.

Свободные игры на устройстве не входят в число серверных партий. В Сапёре текущая реализация хранит только отправленные победы: проигрыши не учитываются, а наличие результата в рейтинге не означает серверную replay-проверку. Ручные исправления исключены из игровых метрик. Снятые результаты остаются в числе партий, но не результатов рейтинга. Удаление старых записей из БД изменит соответствующую историческую статистику; отдельного неизменяемого хранилища агрегатов пока нет.

## Локальная проверка

`TG_GAMES_DEV_OWNER=1` включает фиксированного владельца только в dev API Vite на `127.0.0.1`, с отдельной `.cache/arcade-admin-dev.sqlite`. Обычный dev API остаётся пользователем `1` и использует `.cache/arcade-dev.sqlite`. Поле ID из HTTP body не меняет пользователя. Эти API не входят в production bundle. Для возврата к обычному режиму в PowerShell: `Remove-Item Env:TG_GAMES_DEV_OWNER`.

`npm run test:admin:browser` поднимает два локальных dev-сервера, проверяет владельца и обычного пользователя, реальное снятие тестового результата, повтор после потери ответа и единственную запись журнала, мобильный экран, прямой маршрут и навигацию. Скриншоты сохраняются в `.cache/screenshots/admin-desktop.png` и `admin-mobile.png`. Серверные тесты проверяют все операции снятия, запрет рейтинга, откат транзакции, конфликт предварительного состояния, поиск и границы недель. Сборка cloud modules проверяет отсутствие Node/Bun imports; это не проверка облачной совместимости SQL.
